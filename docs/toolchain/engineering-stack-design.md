# Project engineering environment design

The environment preserves complete pinned source packages and provides a small
project-local interface for installation, verification and harness discovery.
The consumer gets the same source revision in each harness. One lock defines
this environment. This installer supports initial setup and repeated verification
of that lock. A version migration requires a separate reviewed change to sources
and generated artifacts. It does not overwrite an earlier environment or remove
stale skill directories.

## Caller usage and data

The proposed tooling exposes install, verify, inspect and launch actions through
one PowerShell command. Installation prepares sources and Codex project skills.
Verification reads them without changing them. Inspection invokes native harness
metadata interfaces. Claude launch adds session-only plugin directory arguments.
Initial source hydration uses an unpublished staging directory. Source groups
become visible at their final path only after full verification. Failed attempts
retain an ownership receipt and their staging artifacts for review. A retry
starts another bounded attempt rather than trusting a partially created checkout.

The lock owns source commit, tree, full package scope and blob/SHA-256 inventories.
The generated catalog owns skill identities and pristine entrypoint paths.
Compatibility policy owns harness mappings and supported/dormant/unsupported
capabilities. Receipts own observed outcomes and limitations.

## Compared shapes and synthesis

Two fresh read-only design agents independently examined the integration. The
available inherited model supplied both contexts. A cross-family judge did not
run because the requested Grok/Claude model families were unavailable here.

| Criterion | Project wrappers in both harnesses | Native plugins in both harnesses | Selected hybrid |
| --- | --- | --- | --- |
| Exact full source identity | Verifiable | Verifiable | Verifiable through one lock |
| Native discovery | Codex documented; Claude project wrapper discovery needs additional proof | Claude session plugin loading demonstrated; equivalent Codex local plugin option unproven | Use each demonstrated mechanism |
| Preserve support resources | Read pristine sources via wrapper pointers | Native packages preserve their own layout | Preserve canonical and generated packages |
| Agent registration | Reference prompts unless separately registered | Claude discovers packaged agents | Native Claude agents, disclosed Codex prompt adaptation |
| Global installation/update state | Can avoid it | Marketplace installation adds cache/update concerns | Project wrappers and session plugin arguments avoid global installation |
| Maintenance | Duplicate projections across both harnesses | Harness installation differences remain | One lock and catalog, one wrapper projection |

The base is one source-preserving environment owner. Graft the wrapper candidate's
deterministic catalog and ownership checks for Codex. Graft the native candidate's
Claude plugin loading, which exposes packaged agents and namespaces without
copying skills. Reject Claude wrappers because the native loader is available.
Reject a symmetric marketplace installation because its Codex/project behavior
was not established and automatic update semantics conflict with immutable pins.

## Source boundary

The inventory contains Pocock's complete repository, PStack's complete canonical
package, its same-commit generated Claude harness tree, and the same-commit
complete Team Kit package. The generated harness intentionally omits canonical
automations/assets and rewrites some links to `main`. Retain both trees and map
those references locally. Source inclusion executes nothing.

Only promoted Pocock manifest entries and the PStack/Team Kit plugin skill
directories become entrypoints. Other source remains available for review.
Automation registration, external services, model-rule changes and global hook
installation remain separate operations. The setup does not create a Codex chat.

## Throughput checkpoint

- Blocking first steps. Verify source identities and compare two design shapes
  before generating adapters.
- Independent workstreams. The tooling worker owns scripts and generated
  entrypoints. The parent owns locks, compatibility, project guidance and receipts.
- Shared mutable state. Both use one isolated worktree and disjoint file fences.
  Serialize final verification and integration after the worker returns.
- Smallest safe decomposition. One worker implements the coupled loader,
  generator and verifier. Independent reviewers inspect the completed diff.

## Verification contract

Source verification covers every locked blob and detects drift. Reinstallation
must leave generated bytes unchanged. Verification must fail on a deliberately
changed owned fixture and pass after restoration. Native Codex discovery must
report the expected unique project entrypoints. Claude metadata must report the
pinned plugin skills and agents through session-only loading. Those checks do
not claim model execution, desktop plugin adoption or Workbench runtime behavior.

The operation follows PStack Feature with architecture exploration, delegated
implementation, deslop, fresh comment/reliability review and a ready PR. The
default model panel is unavailable through Codex's collaboration schema. A
separate native Claude CLI review is recorded separately. Existing source-connection
experiments are evidence to preserve, not tests to repeat for this setup.
